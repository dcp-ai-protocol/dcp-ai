# Governance プロファイル

> [英語の仕様](../../../../../spec/profiles/governance/README.md)の参考訳です（25/10/2026 更新）。**規範となるのは英語版です**。この翻訳に規範的な効力はなく、内容が異なる場合は英語版が優先されます。識別子とコードブロックは翻訳せずにそのまま掲載しています。

**状態：** 公開済み — v2.0  
**範囲：** リスクティア、管轄区域の証明、失効、鍵の回復、ガバナンスの運用  

---

<a id="purpose"></a>

## 目的

DCP コアはアーティファクトと検証のモデルを定義します。Governance プロファイルは、それらのアーティファクトがライフサイクルを通じてどう管理されるかを決めるポリシー、規則、運用の仕組みを定義します。誰がエージェントを失効させられるか、リスクの水準をどう割り当てるか、どの管轄区域の要件が適用されるか、鍵をどう回復するかです。

これは明示的にコアの外にあります。理由は次のとおりです：

- ガバナンスのポリシーは展開に依存する（政府の展開とスタートアップでは規則が異なる）
- リスクティアの割り当ては、プロトコルの構造ではなく検証器の文脈に依存する
- 管轄区域の要件は、国や規制の枠組みによって異なる
- 鍵の回復と失効の仕組みには運用のインフラが関わる
- ガバナンスの儀式には、検証を超える複数の当事者の調整が必要

<a id="what-lives-here-not-in-core"></a>

## ここにあるもの（コアにはない）

<a id="adaptive-security-tiers"></a>

### 適応的なセキュリティティア

意図のリスクスコア、データの分類、行動の種類に基づいて暗号の保護の水準を自動で選ぶ、4 段階の仕組み（routine、standard、elevated、maximum）。

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 14 節を参照してください。

<a id="jurisdiction-attestation"></a>

### 管轄区域の証明

特定の管轄区域について、プリンシパルの結び付けの記録の中のアイデンティティを証明する、政府または認定された権限者による省略可能な証明。

[DCP-01](../../../../../spec/DCP-01.md) の「Jurisdiction Attestation」の節を参照してください。

<a id="revocation"></a>

### 失効

エージェントを失効させる仕組み：

- 署名された Revocation Record による**標準の失効**（[DCP-01](../../../../../spec/DCP-01.md)）
- 事前に登録した失効のトークンによる**緊急の失効**（署名は不要）
- 権限者が公開する**管轄区域の失効のリスト**

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 11.3 節と [AUDIT の報告](../../../../../spec/AUDIT-v2.0-FINAL.md) の欠落 13 を参照してください。

<a id="key-recovery"></a>

### 鍵の回復

シャミアの秘密分散を使い、分け前をハイブリッドの KEM で暗号化する、M-of-N のソーシャルな回復。

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 11.2 節と [AUDIT の報告](../../../../../spec/AUDIT-v2.0-FINAL.md) の欠落 1 を参照してください。

<a id="key-rotation"></a>

### 鍵のローテーション

ローテーションの儀式：新しい鍵が所有の証明に署名し、古い鍵が認可に副署し、猶予期間を設定できる。

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 11.1 節を参照してください。

<a id="governance-key-ceremonies"></a>

### ガバナンスの鍵の儀式

アルゴリズムのアドバイザリーやプロトコルの決定に署名するための、複数の当事者による M-of-N のガバナンスの運用。

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 13.1 節と [AUDIT の報告](../../../../../spec/AUDIT-v2.0-FINAL.md) の「Governance Key Ceremony」を参照してください。

<a id="verifier-authoritative-policy"></a>

### 検証器が決定権を持つポリシー

署名のポリシーはエージェントではなく検証器の設定で決まるという原則。セキュリティティアを決して下げないという規則を含みます。

[DCP-AI v2.0](../../../../../spec/DCP-AI-v2.0.md) の 7.2 節を参照してください。

<a id="what-stays-in-core"></a>

## コアに残るもの

- プリンシパルの結び付けの中の失効の約束の存在（`revocation_token` のフィールド）
- エージェントのパスポートの `status` のフィールド（active/suspended/revoked）
- ポリシーの結果のアーティファクト（ただしポリシー判断がどう下されるかは含まない）
- 監査証跡（ただしどのガバナンスのイベントを記録するかは含まない）

<a id="implementation-notes-informative"></a>

## 実装に関する注記（参考）

> **2026 年 10 月 25 日に追加。規範的ではありません。** これらの注記は要件を加えず、上の内容を何も変えません。`main` のリファレンスの
> コードがこの文書とどう関係するかを説明するものです。食い違う場合は、上の規範的な本文がそのまま有効です。

- どちらの RPR のスキーマにも `revocation_token` のフィールドはありません。V2 のパスポートのスキーマには、省略可能な
  `emergency_revocation_token` があり、緊急の失効が確認する約束です。V1 のパスポートにはありません。
- パスポートの `status` の列挙値は、V1 では `active`、`suspended`、`revoked` で、V2 ではさらに `commissioned`、`declining`、
  `decommissioned` が加わります（6 つの状態）。
- SDK の鍵の回復のヘルパーは、シャミアの方式で秘密を分割して再構成し、分け前をそのまま返します。
  分け前をハイブリッドの KEM で暗号化したり配布したりはしません。各分け前を暗号化して届けるのは
  呼び出し元の仕事です。
