# DCP-AI のガバナンス

> [英語版](../../GOVERNANCE.md)の参考訳です（25/10/2026 更新）。内容が異なる場合は英語版が優先されます。識別子、コマンド、コードブロックは翻訳せずにそのまま掲載しています。

この文書は、DCP-AI（Digital Citizenship Protocol for AI Agents）プロジェクトのガバナンスのモデルを説明します。

<a id="governance-model"></a>

## ガバナンスのモデル

DCP-AI は**オープンなガバナンス**のモデルを採用しています。プロジェクトは公開の場で開発され、誰からの貢献も歓迎します。重要な決定は、コミュニティの意見を踏まえ、メンテナーの間の合意によって行われます。

**現在の状態（2026 年 4 月）：** プロジェクトは立ち上げの段階にあり、創設時のメンテナーが 1 人だけです。以下に述べる役割、意思決定の手順、投票の規則は、メンテナーが加わっていくにつれてプロジェクトがどう運営されるかを定めます。プロジェクトのメンテナーが 1 人の間は、「メンテナーの間の合意」はそのメンテナーの決定を意味し、この文書はその場合にも構造上そのまま当てはまります。

<a id="roles"></a>

## 役割

<a id="contributors"></a>

### コントリビューター

プルリクエストを送る、issue を作る、議論に参加する、あるいはほかの形でプロジェクトに貢献する人は誰でもコントリビューターです。コントリビューターは[コントリビューションガイド](../../CONTRIBUTING.md)に従うことが求められます。

<a id="reviewers"></a>

### レビュアー

継続的で質の高い貢献と、プロトコルへの確かな理解を示した、信頼されるコントリビューターです。レビュアーは次のことができます：

- プルリクエストを承認する
- issue をトリアージし、ラベルを付ける
- 設計の議論に、より大きな重みを持って参加する

レビュアーはメンテナーが推薦し、合意によって承認されます。

<a id="maintainers"></a>

### メンテナー

メンテナーはリポジトリへの完全な書き込み権限を持ち、プロジェクト全体の方向性に責任を負います。メンテナーは次のことができます：

- プルリクエストをマージする
- リリースを作る
- CI/CD とインフラを管理する
- 新しいレビュアーとメンテナーを推薦し、承認する
- 合意に達しないときに最終的な決定を下す

新しいメンテナーは、既存のメンテナー全員の同意によって加わります。

<a id="decision-making-process"></a>

## 意思決定の手順

1. **提案**：重要な変更（プロトコルの新しいバージョン、互換性を壊す変更、新しい SDK、ガバナンスの変更）は、実装の前に GitHub の issue または discussion として提案するべきです。

2. **議論**：すべての関係者が意見を出すことが推奨されます。重要な提案については、最低 7 日間の議論の期間を設けてください。

3. **合意**：決定はメンテナーの間の合意によって行われます。合意とは、議論の後に異議を持ち続けるメンテナーがいないことを意味します。

4. **投票**：合意に達しない場合は、メンテナーの間の単純多数決で結果を決めます。各メンテナーは 1 票を持ちます。投票は少なくとも 72 時間開いていなければなりません。

5. **記録**：重要な決定はすべて、関係する issue、PR、または議論のスレッドに記録されます。

<a id="protocol-changes"></a>

## プロトコルの変更

プロトコルの規範的な仕様（`spec/`）の変更には、より高い基準が求められます：

- 変更、動機、後方互換性への影響を説明する文書による提案
- 少なくとも 2 人のメンテナーによるレビュー
- 互換性を壊す変更については、最低 14 日間の議論の期間
- 新しい動作を検証する、更新された適合性テスト
- `schemas/v1/` または `schemas/v2/`（または新しいバージョンのディレクトリ）の更新されたスキーマ

<a id="release-process"></a>

## リリースの手順

1. **バージョン管理**：プロジェクトは [Semantic Versioning](https://semver.org/) に従います。プロトコルのバージョン（たとえば DCP v1.0）は、実装のバージョンとは別です。

2. **リリースの頻度**：リリースは必要に応じて行います。決まった予定はありません。

3. **リリースの手順**：
   - `main` ですべての CI のチェックが通っていなければならない
   - メンテナーがリリースのブランチを作る（該当する場合）か、`main` からタグを付ける
   - `CHANGELOG.md` をすべての注目すべき変更で更新する
   - リリースノートを GitHub で公開する
   - SDK のパッケージをそれぞれのレジストリ（npm、PyPI、crates.io）に公開する。Go の SDK は中央のレジストリには公開されない。Go のモジュールは `github.com/dcp-ai-protocol/dcp-ai/sdks/go/v2` のタグによって見つけられ、pkg.go.dev がそこから自動的にインデックスする。
   - 公開は `publish.yml`、`publish-pypi.yml`、`publish-integrations.yml`、`publish-templates.yml`、`publish-docker.yml` のワークフローで自動化されており、GitHub Release で起動されるか、手動で実行される。パッケージのワークフローはレジストリに既存のバージョンがあるかを確認するが、Docker のワークフローはそのバージョンの存在確認なしにイメージをビルドしてプッシュする。`publish-docker.yml` は、`server/`、`services/`、`lib/`、`tools/`、`schemas/`、`docker/Dockerfile`、またはワークフロー自体に触れる `main` へのすべてのプッシュでも実行され、`:latest`、`:main`、`:sha-…` のイメージのタグをプッシュする。
   - 該当する場合は、リリースを学術的な著作で引用できるように、Zenodo のソフトウェアの DOI を作成またはリンクする（[CITATION.cff](../../CITATION.cff) を参照）。

4. **緊急の修正**：重大なセキュリティや正しさの修正は、メンテナーの判断で通常の議論の期間を省略できます。

<a id="security-disclosure-policy"></a>

## セキュリティの開示のポリシー

DCP-AI にセキュリティの脆弱性を見つけた場合：

1. 公開の issue を**作らないでください**。
2. 次のいずれかで非公開で報告してください：
   - メール：**security@dcp-ai.org**
   - GitHub の非公開の脆弱性報告：[security/advisories/new](https://github.com/dcp-ai-protocol/dcp-ai/security/advisories/new)
3. 脆弱性の説明、再現の手順、影響を受けるコンポーネント（プロトコル、特定の SDK、サービス、またはスマートコントラクト）、そして想定される影響の評価を含めてください。
4. メンテナーは 48 時間以内に受領を確認し、修正までの見込みの日程を共有します。
5. 修正が出た後に、セキュリティアドバイザリーが公開されます。

詳細は、範囲、SLA、深刻度の扱いを含め、[SECURITY.md](../../SECURITY.md) を参照してください。金銭的な報酬は、決まった報奨金の段階としてではなく、個別に扱われます。

> **注記（2026 年 10 月 25 日）：文書の間で記述が食い違っています。** [SECURITY.md](../../SECURITY.md) は深刻度ごとに決まった報酬の範囲を挙げていますが、この文書と [docs/EARLY_ADOPTERS.md](../../docs/EARLY_ADOPTERS.md) は、報酬は個別に決めるとしています。どちらが適用されるかをメンテナーが確認するまで、両方の記述を残しています。

<a id="amendments"></a>

## 改訂

このガバナンスの文書は、通常の意思決定の手順に従い、最低 14 日間の議論の期間を経て、メンテナーの間の合意によって改訂できます。
